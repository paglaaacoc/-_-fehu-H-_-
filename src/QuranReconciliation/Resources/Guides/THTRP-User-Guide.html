Key terminology

1. What this workstation is

The Holy Quran TRP is a private, offline-first Windows research workstation for The Holy Translation Reconciliation Project. It brings canonical Qur'anic text, selected translations and supporting research tools together while preserving your own developing translation decisions and their history.

It has two fundamentally different layers. The primary research workspace contains your editable work: Context segmentation, notes, translation/reconciliation Working Slices and History. The Context Atlas contains outside proposals and read-only inspection tools. An AI proposal is not an amendment to your research and cannot silently become one.

Foundation: the 114 Surahs, 6,236 Ayat and canonical Arabic source data are not editable through research actions. Interpretation, Context boundaries and source comparisons are proposals and human research choices, not changes to the Qur'an itself.

2. First run and safe setup

  1. Extract the complete Windows ZIP to a dedicated writable folder; do not run the executable from inside the compressed archive.
  2. Keep the provided Corpus, Fonts and associated application files together. Missing companion files cause incomplete or unavailable evidence.
  3. Launch The Holy Quran TRP.exe. Allow local workspace initialization to finish.
  4. Check the build label under the title. For this guide it should identify Build 1.9 R5.
  5. Choose a comfortable theme and font zoom. Review the three Arabic-script display toggles before starting.
  6. Use Data safety → Create verified backup before significant experimental changes, and keep additional backup copies outside the application folder.

The Windows SmartScreen warning sometimes shown for an unsigned executable concerns publisher reputation; it does not prove the application is infected or certify it is safe. Verify the ZIP's source and hash before deciding whether to run it.

3. Qur'an reading and navigation

Surah, Juz and Ayah

Use the Surah list to navigate among the 114 Surahs. The Juz selector provides traditional reading-position awareness; a Juz boundary does not necessarily mark a discourse or research Context boundary. Navigate to a relevant Ayah and read the Arabic before deciding what its semantic unit is.

Arabic presentation

The top toolbar offers Uthmani, IndoPak and IndoPak Nastaleeq display options. These are visual scripts drawn from the bundled source files; choosing a script does not alter the original Ayah data. Script visibility may be toggled without losing current research.

Translations and sources

The research workspace permits selecting appropriate translation and tafsir/source resources. For structural boundary research, keep the controlling Arabic evidence clear and distinguish a translation's wording from the Arabic. Some legacy records include source footnotes: read these with the verse rather than treating them as separate Ayat.

4. Research Context Map

The editable Context Map organizes a Surah into consecutive research passages. A Context Block represents Ayat that should normally be studied together to understand the same immediate discourse. Research boundaries are editable; they are distinct from fixed Surah and Juz divisions.

  1. Choose a Surah and inspect its current Context Block list.
  2. Select the passage you wish to work on; confirm its start and end Ayat in the source text.
  3. When evidence supports it, use the existing Context Map controls to split or merge passages. Do not split merely to fit a preferred length.
  4. Update status and notes to record why you made a decision, rather than relying on a label alone.
  5. Review the resulting passage adjacency and any affected Working Slices. Take a verified backup before large structural edits.

Existing research constraints and protected write paths take precedence over any AI proposal. The app's History and provenance help distinguish current state from earlier decisions.

5. Notes, statuses and provenance

Ayah notes, Context notes and their revisions are persistent parts of your research. Select the correct Ayah or Context before editing. Use each note to record interpretive questions, source comparisons and the reasoning behind a boundary or translation choice. Apply status labels consistently; a status should represent your actual level of review, not an AI model's confidence.

Where the interface marks unsaved or dirty state, your edits are retained under their original Ayah/Context identity across routine navigation and can be restored as recoverable drafts after restarting. They are not canonical until you explicitly Save. History contains saved prior work and timestamps; the Context Atlas sidebar deliberately provides read-only snapshots rather than a second editor.

6. Working Slices

Working Slices are durable reconciliation units. Multiple slices can coexist, be at different stages and be resumed independently. A slice has a defined Surah-local range, notes/work and revision history.

  1. Start from an appropriate existing research Context using New from selected Context… where available.
  2. Confirm the passage range; a Working Slice is not automatically the same as a Context Atlas proposal.
  3. Inspect the Arabic source and selected translations side by side as you work.
  4. Save intentional changes and use the slice's explicit status/revision tools to track development.
  5. Revisit earlier slices through the Working Slices or History workspace, rather than creating unnecessary duplicates.

Deletions and historical removals have specific safety semantics; do not assume a removed slice has been physically wiped from all historical records. Rely on the app's available History and backup controls.

7. Organized research History

The History workspace contains research activity, changes and version context, with search, filters and organized/timeline browsing. Use it when you need to recover the reason for a past decision or return to work you previously completed.

A useful pattern is to review History before changing an established Context boundary. The current record alone may not explain why a boundary was originally chosen. Backups protect complete research data; History and immutable revisions answer different questions and should not be mistaken for backup files.

8. Context Atlas overview

Context Atlas is the read-only Proposal Corpus workspace. The selected corpus can be the bundled proposal or a separately imported independent or revised proposal. Atlas actions provide browsing, review, cross-Surah worksets, comparison, provenance and new/revision research handoffs.

Atlas areaWhat it does
BrowseRead the selected proposal's fine Context Blocks, rationale and Macro Groups by Surah.
Related WorksetsInspect explicitly proposed thematic relationships across Surahs; these do not merge canonical Ayah ranges.
ReviewFind important or uncertain proposal records, with lazy native cards to avoid building the entire list at once.
CompareInspect two chosen corpora at the same Ayah boundary and see actual Context Blocks and reasoning on both sides.
PinsKeep up to 40 Ayat/Context passages temporarily in a session comparison tray.
ProvenanceRead corpus identity, edition, model/contributor and source metadata.

Read Ayat is available from many Atlas results. It opens local Qur'an evidence without creating a Working Slice, changing segmentation or writing notes.

9. Comparing Context proposals — Build 1.9 R5

  1. Import a second validated Proposal Corpus or choose any two already available corpora.
  2. Open Context Atlas → Compare and choose Corpus A and Corpus B.
  3. Use the Surah list to focus the comparison. The overview reports shared, A-only and B-only boundaries and exact matching fine ranges.
  4. Use Previous difference and Next difference to inspect one disputed Ayah transition at a time.
  5. Read the actual Contexts containing the Ayah before and after the transition, their coherence notes, boundary reasons and Macro Group labels side by side.
  6. Choose Read Ayat side by side (or Read A/B Ayat from either column) to open two independently scrollable canonical Arabic readers. Each follows its own corpus's actual Context boundaries, while marking the disputed Ayah transition in both.
  7. Optionally select one English or Bengali translation for both panes; the sources, zoom and Arabic-script controls apply consistently. Choose Back to Compare without altering research state.
  8. Use Ayah Evidence or Pin Context for closer analysis.

Session restoration: when you switch from Context Atlas to Research, Working Slices, History, or another app workspace and return during the same launch, Atlas keeps the selected tab, Corpus A/B choices, Surah, disagreement and reading/scroll position. Pins remain session-only. Explicitly importing or removing a corpus refreshes the list; a removed corpus cannot be restored and receives a safe fallback.

An A-only boundary means Corpus A separates Ayat at that position while B keeps them within one fine Context. A B-only boundary means the reverse. Neither is automatically right. The comparison is aligned by Ayah reference, not by Context Block ordinal number: Context 3 in one corpus need not correspond to Context 3 in another.

Compare is for evaluation, never automatic reconciliation. It does not promote either AI proposal into editable owner research.

10. Pin & Compare — Build 1.9 R5

Use Pin from an Atlas Context card, Pin Context from Compare, or Pin this Ayah from an open Read Ayat preview. Pins form a temporary list that can contain passages from several Surahs.

Open the Pins tab. Select any stored passage as A and another as B. The pinned comparison shows bounded local Uthmani Arabic evidence for up to the first three Ayat of each passage. Use Read full passage for a long Context. You can remove a pin or clear the session tray. There is a safety cap of 40 entries.

Nothing in Pins is saved to research.sqlite. Pins are intentionally discarded after you close the application. Do not use this tray as a substitute for durable notes, Working Slices or bookmarks.

11. Ayah Evidence — Build 1.9 R5

From Read Ayat or a Compare disagreement, select Ayah Evidence for an individual Ayah. This opens a read-only window containing existing local word-by-word positions, Arabic words, transliterations and English word meanings, plus research Context overlap, note counts and Working Slice references where available.

The evidence view uses the existing local word-by-word database and a SELECT-only summary of your research database. It neither edits notes nor assumes a proposed Context is correct. Word meanings and transliterations are reference aids, not substitutes for interpreting the Arabic sentence and larger discourse.

12. Read in surrounding Context — Build 1.9 R5

While Read Ayat is open, select Show up to 3 Ayat before and after (outside selected Context) to view neighboring evidence at the passage boundary. The feature automatically stops at a Surah edge. Surrounding Ayat use a different background and display an explicit Outside selected Context label.

These neighboring Ayat remain outside the selected proposal block. Their presence does not redefine the Context boundary or affect saved research. Uncheck the option to return to the selected passage alone. The preview remains lazy and its translation-source selectors can still be used.

13. New and Improve AI research handoffs

New Proposal Handoff

From the Atlas Export Handoff menu, choose New Proposal Handoff to create a self-contained evidence pack for an entirely independent research process. It includes Arabic evidence, the optional narrow English helper, terminology, exact app-native schemas, a detailed model prompt, and a validation script. It deliberately does not include an existing Proposal Corpus.

Improve Existing Proposal Corpus

Select the specific parent corpus, then choose Improve Existing Proposal Corpus…. The exported pack includes that parent and its exact lineage hash, a dedicated revision prompt, a changelog template and common evidence. The revised proposal must use a new ID and edition; it must not overwrite the parent. Independence and revision are fundamentally different research assignments.

Instructions for the AI research chat

The ZIP includes its own 01-MASTER-PROMPT.md and 02-IMPORT-PACKAGE-CONTRACT.md. Ask the research model to read both and actually complete its file-based analysis, rather than only drafting a plan. Require it to save after each Surah, validate per-Surah outputs, run the final complete ZIP validator, and return separate import and research-continuity ZIP files.

14. Importing Proposal Corpora safely

  1. Obtain a trusted ZIP that contains manifest.json and proposal-corpus.json at its root.
  2. Run the supplied Python preflight if available, but remember that it cannot replace the application's final native importer.
  3. Choose Context Atlas → Import Proposal Corpus…, select the ZIP and await validation.
  4. Verify the imported display name, contributor, source information and expected Surah content in Browse and Provenance.
  5. When appropriate, use Compare to evaluate the new corpus against another, without applying it to your research.

A package with an incorrect payload hash, conflicting corpus identity or malformed ranges should be refused. A repeated import of byte-identical content can be reported as already present. Removing an imported corpus deletes only its isolated imported proposal package, not your research notes, saved Contexts, Working Slices or built-in proposal.

15. Data safety, verified backup, restore and reset

Ask before closing app: Open Data safety and check or uncheck the routine close-confirmation option. Enabled by default, this setting remembers your preference. Uncommitted research is guarded independently: even if routine confirmation is off, an ordinary Windows close asks before leaving with drafts. Changes to Working Slices, Ayah notes, and Context notes are separately checkpointed to portable Data/recoverable-drafts.json while you type and before ordinary navigation/close; restart restores drafts to their original editors, not automatically to committed research.

Recoverable drafts are NOT saved research: they do not create SQLite revisions, and the verified owner-data backup deliberately includes committed research and settings only. Review and explicitly Save recovered drafts after restarting. Periodic checkpoints reduce unexpected-shutdown losses, but the most recent unsaved keystrokes can still be lost during sudden power failure; create verified backups for committed research. A malformed or future-schema draft file is preserved and refused instead of silently overwritten. Deliberately discarding drafts before restore/reset clears their recovery sidecar; if that cannot be completed, the destructive operation stops.

The bottom navigation contains Data safety with verified backup, restore and reset controls. Treat these as high-consequence operations, not routine appearance preferences.

  1. Before meaningful research or substantial changes, use Create verified backup and ensure the backup completes successfully.
  2. Store a copy outside the active workstation directory—ideally on another storage device or protected location.
  3. Before restore, verify that you selected the intended backup. Restoration replaces active research state according to the application's existing guarded process.
  4. Before reset, make and independently preserve a verified backup. Read every destructive-operation confirmation carefully.
  5. Never overwrite the app's generated research files by manually copying individual SQLite files while the program is open.
Research safety priority: Backup protects durable owner research. The Atlas ZIP is a separate proposed scholarship package and must not be confused with a verified backup of your work.

16. Portable folders, relocation and migration

This is a portable Windows workstation. Keep the executable, bundled corpus, source fonts and generated folders together when moving between computers or locations. Prefer closing the app, making a verified research backup, and copying the complete application folder rather than only the EXE.

The app may create Data/, Backups/, Diagnostics/, Context Atlas imported packages and exports next to its portable installation. These generated folders hold your local state and must not be accidentally included in any public development/CI mirror.

A newly downloaded build ZIP is not automatically your existing work. Restore or migrate owner data deliberately using the accepted backup procedures. Never blindly replace a newer research database with an older copy.

17. Themes, zoom and layout

Theme and Zoom remain in the top toolbar because they are frequent reading controls. The application offers light, night and OLED variants. Arabic script toggles also remain visible in the top bar.

Use the Layout menu to show/hide sidebars, choose full/compact/hidden top bar and reset panel widths. Research and Atlas preview content should wrap when zoomed or when the window width changes. On a 34-inch ultrawide, the Atlas Compare view can show two large columns; at a narrower width it stacks the paired cards.

If a long passage or translation seems clipped, try expanding the center reading area using the splitters or show fewer sidebars. If it persists, note the version, monitor resolution, scaling, Surah and Ayah range before reporting it.

18. Practical research workflows

A. Review a proposed Context disagreement

  1. Open Atlas Compare and select two corpora.
  2. Choose a Surah and the next disputed boundary.
  3. Read both Context coherence notes and the reason each corpus splits or joins that passage.
  4. Read the actual Arabic around the transition; optionally enable surrounding evidence.
  5. Inspect Ayah Evidence where lexical details matter.
  6. Record your own conclusion in persistent Research, not in the temporary Atlas display.

B. Track a cross-Surah structural idea

  1. Open Related Worksets and inspect the proposed members/subsets.
  2. Pin two particularly relevant passages from different Surahs.
  3. Use the Pins tray to read them side by side, then inspect the full Contexts.
  4. Preserve your evaluation in your own notes or Working Slices as appropriate.

C. Commission a fully independent AI Context analysis

  1. Export New Proposal Handoff, not Improve Existing.
  2. Attach only that handoff to the independent research chat.
  3. Require Arabic-first research and persisted 114-Surah checkpoints.
  4. Validate and import the resulting proposal ZIP in the Atlas.
  5. Treat the result as a new proposed scholarly view, never an authoritative replacement of existing research.

D. Refine a previous proposal deliberately

Export Improve Existing for the exact parent, require a new edition, a source-grounded changelog and exact lineage, verify import compatibility, and keep both old and new proposals available for inspection.

19. Troubleshooting and FAQs

Why can I see an imported proposal but not edit its Context Blocks?

Context Atlas is intentionally read-only. Edit your own Context Map in Research; imported proposal boundaries are not owner research state.

Why is a ZIP rejected even if JSON validation passes?

The production importer enforces exact native fields, SHA-256 matching, Surah coverage, boundaries, Macro partition and related-workset references. Use the enclosed final-package validator before attempting import.

Why don't the A and B Context numbers line up?

Two proposals can split the same Surah differently. Compare is Ayah-aligned: it shows passages containing the same transition, not blocks with coincidentally matching indices.

Where did my pins go after restarting?

Pins are session-only by design, not durable research records. Record important decisions in Research or Working Slices.

Why is an Ayah visibly outside the selected Context?

You enabled surrounding evidence. It is shown for interpretation of a boundary; it is not part of the selected proposed range.

Why is the application or Review tab sluggish?

The reading and Review cards load progressively. If performance degrades, record your scale, window size, tab, specific Surah and corpus; do not repeatedly reinstall or reset user data as a first diagnostic step.

What if the word evidence pane shows missing content?

Confirm the original word-by-word companion database remains with the application. The evidence inspector reads existing source data only and safely closes when unavailable.

How do I return to previous work?

Use History and the Working Slices workspace, not a manually edited copy of SQLite. Restore only with a verified backup after reviewing its effects.

What if the icon looks blurry in Explorer?

That is a Windows icon-size or cached-thumbnail issue, separate from Qur'anic source fidelity. Prefer original high-resolution icon source if available; changing resources in an accepted EXE changes its checksum.
